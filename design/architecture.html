MoveMent · architecture

How MoveMent is built

MoveMent is a local-first web app. The code is downloaded to your phone once, and your data never leaves it. With no server of our own, it costs nothing to run.

Five layers, one direction

Each layer may only use the layers below it. The build runs a check script that fails if a file breaks this rule, so the structure can't quietly erode.

app/The shellTab bar, switching screens, which screen is openuses everything
features/The app's areastoday · food · training · progress · settings · body. Each has its screens and its own database actions.data · ui · lib
not each other*
data/The databaseTable definitions, settings, live-updating querieslib
ui/Building blocksIcon, Dial, Sheet, Toast, charts. Knows nothing about MoveMent, so you can reuse it in future apps.lib
lib/Pure math and formattingDates, number formatting, macro totals, estimated 1-rep max. No React, no database.nothing

* Exception: features/body (the weigh-in sheet) is shared because both Today and Progress use it.

Inside a feature

Every feature follows the same three-part pattern, shown here with food.

Screens & sheetsFoodScreen, EditLogSheet, add/*Draw the page. Read data with live queries that update on their own.
ActionsfoodActions.tsThe only place this feature writes to the database: logFood, copyDay, updateLog, removeLog.
Outside servicesfoodApi.tsTalks to Open Food Facts and USDA and turns their answers into MoveMent foods.
reads ↓ data/ · writes → actionswrites ↓ data/fetches ↗ internet

Why it helps: when something saves wrong, there's exactly one file to look in. Screens stay simple because they never juggle saving and re-loading.

One action, start to finish: logging a food

YouPick “Protein bar”, enter 2 servings, tap Add to breakfast.
AmountStep.tsx (screen)Calls logFood(food, 120 g, "breakfast", today). It doesn't touch the database itself.
foodActions.tsSaves the food if it's new, or bumps it up your “Recent” list.
foodActions.ts → IndexedDBAdds a food log with its own copy of the calories and macros, so editing the food later never changes past days.
IndexedDB → live queriesEvery screen watching today's logs is told something changed.
Today + Food screensDials, totals and meal list redraw with the new numbers. No manual refresh code anywhere.

Data model

Eight tables in the phone's database. Orange fields point to another table.

foods food definitions

  • id
  • name, brand, barcode
  • source off · usda · custom
  • per100 kcal p c f
  • servingG, servingLabel
  • lastUsed, useCount

foodLogs what you ate

  • id
  • date YYYY-MM-DD
  • meal
  • foodId → foods
  • name, grams
  • kcal p c f (snapshot)

exercises the catalog

  • id
  • name
  • kind weight · bodyweight · cardio

routines saved plans

  • id, name
  • items[]
  •   exerciseId → exercises
  •   sets, reps

workouts sessions

  • id, name, date
  • routineId → routines
  • startedAt
  • finishedAt (empty = in progress)

sets every set

  • id, order
  • workoutId → workouts
  • exerciseId → exercises
  • weight, reps · minutes, distance
  • done

weights weigh-ins

  • date (one per day)
  • weight

settings key → value

  • targets kcal p c f
  • unit lb · kg
  • usdaKey, lastBackup

Changing tables means adding a new schema version in data/db.ts. Phones that already have data upgrade one step at a time, so nothing is lost.

Where new things go

You're adding…Put it in
A new area, like Activity / Apple Health importfeatures/activity/ with a screen and activityActions.ts, plus a tab in app/routes.ts
A new kind of dataA new schema version in data/db.ts
A generic widget (new chart, picker, button style)ui/, colored from styles/tokens.css
A calculation (TDEE, pace, streaks)lib/ as a pure function
Something two features both needA shared feature like features/body, added to the check script's shared list
